# 00A_여행블로그_AUTOMATION_FIRST — 자동화 우선 운영 규칙

> 목적: 사용자가 중간 단계마다 승인·파일 찾기·Work 이동·이미지 검수를 반복하지 않아도, 시작 신호 한 번으로 한 글을 끝까지 처리한다.
> 이 파일은 여행블로그 자동화 작업에서 MASTER 바로 다음 우선순위로 적용한다.

## 1. 기본 목표
- 사용자가 `다음 글`, `진행`, `이어줘`, `발행 진행`처럼 시작 신호를 주면 **한 글을 끝까지 처리**하는 것이 기본이다.
- 목표 흐름: `Git 원고/STATUS 확인 → 본문 검수 → 사실·링크 확인 → 이미지 제작/자체검수 → Work 1회 실행 → 네이버 반영 → 최종검수 → 발행 또는 지정 종료점 보고`.
- 사용자가 중간 승인이나 개별 이미지 확인을 명시적으로 요청하지 않는 한 **단계별 승인 질문을 하지 않는다**.
- 사용자에게 파일 위치 확인, 같은 규칙 재설명, 이미 확보된 소스 재업로드를 반복 요구하지 않는다.

## 2. 사용자 개입은 예외일 때만
다음처럼 사람이 꼭 필요한 경우에만 사용자에게 요청한다.
- 로그인/보호조치/보안 인증
- 실제로 접근할 수 없는 비공개 원본
- 법적·권리상 사용 가능 여부가 확인되지 않는 자료
- 서로 충돌하는 사실 중 근거로 해소할 수 없는 경우
- 사용자가 직접 선택해야 하는 명시적 취향/정책 결정
그 외에는 ChatGPT가 자체 판단·검수 후 계속 진행한다.

## 3. 이미지 자동화 원칙
- 이미지마다 사용자 승인받는 흐름을 기본값으로 두지 않는다.
- `area2.md` + `photos/CREDITS.md` + 프로젝트 이미지 지침을 읽고 **정해진 비율·문구·소스·스타일로 일괄 제작**한다.
- 실제 장소 원본이 있으면 원본을 실제 입력으로 사용하고, 장소를 새로 생성하지 않는다.
- 카드별 소스가 반복되어 시각적으로 단조로우면, 같은 장소의 사용권이 확인된 **다른 실제 원본**을 먼저 찾는다.
- 한 이미지 생성 후 다음을 자체검수한다: 문구/숫자/비율/출처/장소/패널·블러·미백/폰트 위계/모바일 가독성.
- 생성 편집이 실제 원본을 보존하지 못하는 실패가 2회 반복되면 같은 방식으로 계속 재생성하지 않는다. 가능하면 **실제 원본 + 결정론적 텍스트 조판** 방식으로 전환한다.
- 사용자에게 `이 이미지 괜찮아?`를 매 장마다 묻지 않는다. 사용자 피드백이 오면 그 피드백을 다음 전체 세트에 반영한다.

## 4. 템플릿 우선
- 매 글마다 디자인을 새로 발명하지 않는다.
- 승인된 여행 블로그 카드 구조를 재사용한다.
- 기본 세트: `썸네일 1종 + 정보카드 4~6종 + CTA 1종`.
- 사진·문구·포인트색만 글별 지시에 맞게 교체하고, 타이포 위계·여백·금지요소는 고정한다.
- 특정 글에서 사용자가 `이번 글만 사용`이라고 한 이미지는 장기 템플릿으로 승격하지 않는다.

## 5. Work 사용 원칙 — 한 글 한 번
- 원칙적으로 **한 글당 Work 실행 1회**를 목표로 한다.
- Work를 열기 전에 메인 Chat에서 본문, 서식맵, 링크, 이미지 전체 세트, 삽입순서, 종료조건까지 확정한다.
- Work에는 브라우저 실행만 맡긴다. 조사·이미지 생성·디자인 결정은 맡기지 않는다.
- Work 지시문은 항상 **PLAIN TEXT, 바로 복붙 가능 형식**으로 제공한다.
- 같은 UI 동작 2회 실패 시 중단하고 메인 Chat으로 돌아온다. 같은 실패를 새 Work에서 무작정 반복하지 않는다.

## 6. 발행 기본값
- 이 프로젝트의 장기 목표는 `알아서 발행하는 자동화`다.
- 사용자가 `임시저장만`, `발행 금지`, `검수 후 승인`이라고 명시하지 않은 신규 자동화 실행은 **최종 자체검수 후 공개 발행까지**를 목표로 한다.
- 기존 글 복구·민감한 수정·사용자가 임시저장을 지정한 작업은 해당 지시를 우선한다.
- 공개 발행 직전 제목/본문/이미지/링크/대표이미지/모바일 가독성에 치명적 오류가 있으면 발행하지 않고 예외 보고한다.

## 7. 다음 글 시작 신호 해석
사용자가 아래처럼 짧게 말해도 전체 파이프라인 시작으로 해석한다.
- `다음 글`
- `진행`
- `계속`
- `이어줘`
- `발행해줘`

단, 현재 대화에서 특정 부분 작업 범위가 명확하면 그 범위를 우선한다.

## 8. 완료 보고
정상 완료 시 긴 작업 로그를 나열하지 않는다.
- 글 제목
- 발행/임시저장 상태
- 최종 확인 시각
- 예외 또는 남은 항목(있을 때만)
만 짧게 보고한다.

## 9. 감독 루프 금지 / 효율 기준
- **사용자를 중간 감독자로 쓰지 않는다.** 한 글 처리 중 Chat ↔ Work ↔ File Library ↔ 사용자 확인을 반복 왕복하는 흐름은 실패한 자동화로 간주한다.
- 이미 Git, File Library, 프로젝트 소스에 확보된 자료는 사용자가 다시 찾거나 재첨부하게 하지 말고 시스템이 다시 검색한다.
- 같은 종류의 실패가 2회 발생하면 세 번째부터는 같은 방식을 반복하지 않고 더 안정적인 방식으로 전환한다.
  - 이미지 편집 2회 실패 → 승인 템플릿/결정론적 텍스트 조판
  - 네이티브 링크 미리보기 2회 실패 → 일반 클릭 링크
  - Work UI 동일 동작 2회 실패 → 안전 저장 후 새 단일 실행 패킷으로 정리
- 사용자가 한 글을 끝내기 위해 여러 Work 창을 직접 만들고 지시를 계속 옮기는 구조를 정상 운영으로 보지 않는다.
- 한 글당 목표는 **메인 Chat 준비 완료 → Work 1회 → 저장/발행 완료**다.
- 담양 복구 과정처럼 몇 시간 동안 파일 확보·이미지 재생성·Work 왕복을 반복한 사례는 실패 사례로 기록하고, 다음 글에서는 재현하지 않는다.
- 자동화 성공 기준은 작업량이 아니라 **사용자 개입 최소, Work 사용 최소, 시작 신호 한 번으로 완료**다.
- 글 하나에서 비정상 루프가 감지되면 품질을 무한정 미세조정하지 않는다. 치명적 오류만 고치고 승인된 템플릿과 안전한 대체방식으로 완료한다.

## 10. 한 줄 원칙
**사용자가 감독하는 자동화가 아니라, AI가 끝까지 처리하고 예외가 있을 때만 사용자를 부르는 자동화로 운영한다.**
