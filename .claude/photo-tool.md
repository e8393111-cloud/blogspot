# 사진 소스 도구 — 관광사진 API로 배경 사진 확보하기

영역2 카드마다 **실재하는 공공누리 사진 URL**을 붙이는 방법이다.
`.claude/image-guide.md` §0이 "포토코리아 1순위, URL 지어내기 금지"라고 정해 놨지만
**지킬 수단이 없어서** 매번 "소스 미확보"로 넘겨 왔다. 그 수단이 이것이다.

> 이 문서는 `.claude/keyword-tool.md`(키워드 실측)와 같은 성격이다 — **매번 다시 돌리는 방법**.

---

## 무엇을 얻나

| 값 | 의미 |
|---|---|
| `originimgurl` | **원본 사진 URL** (`tong.visitkorea.or.kr/...`) — 그대로 열면 사진이 뜬다 |
| `imgname` | 사진 제목 (예: `강원_철원_고석정국민관광지_전경_04-5.jpg`) |
| `cpyrhtDivCd` | ★**저작권 유형** — 아래 참조 |
| `contentid` | 장소 고유번호. `detailImage2`에 넘길 때 쓴다 |

## ★★가장 중요 — `cpyrhtDivCd`를 반드시 본다

| 값 | 뜻 | 글자 오버레이 |
|---|---|---|
| **`Type1`** | 공공누리 **제1유형** (출처표시) — 상업 이용·**변형 가능** | ✅ **가능** |
| **`Type3`** | 제1유형 + **변경금지** | ❌ **불가** — 얹으면 라이선스 위반 |

**Type3 사진은 글자 없이 원본 그대로만** 본문에 넣을 수 있다.

★2026-09 철원 취재에서 실제로 겪었다 — 맛집 카드 배경으로 쓰려던 **한탄강빵명장이 Type3**였다.
그대로 글자를 얹었으면 위반이었다. **은하수교·순담계곡·송대소·고석정가든도 전부 Type3**다.
같은 지역 안에서도 사진마다 유형이 다르니 **장소 단위가 아니라 사진 단위로** 봐야 한다.

**출처 표기(공공누리 의무)** — 글 안에 한 줄:
```
사진 출처 : 한국관광공사 포토코리아 (공공누리 제1유형)
```

## ★반드시 지킬 4가지 (전부 실제로 겪은 것)

**1. `contentId`는 대문자 I다.** `contentid`로 보내면 통째로 무시되고
`NO_MANDATORY_REQUEST_PARAMETERS_ERROR1(contentId)`가 돌아온다.

**2. Make 배열 인덱스는 1부터다** → `{{6.response.body.items.item[1].contentid}}`.
`[0]`을 쓰면 빈 값이 들어가 위 에러가 난다. (키워드 도구와 같은 함정)

**3. 검색이 0건이면 detailImage2가 반드시 실패한다.** 정상이다.
　모듈 4의 `handleErrors: true`로 흘려보내고, 결과에서 `0장`으로 읽으면 된다.
　**관광지가 아닌 것은 아예 없다** — 터미널·정류장·시내버스·일반 식당은 등재 대상이 아니다.
　철원에서 `동송터미널`·`동서울터미널`·`소문난순대국왕족발`이 전부 0건이었다. 억지로 다른 사진을 붙이지 않는다.

**4. `parseResponse: false` + 뒤에 `json:ParseJSON`.** 바로 파싱하면 값이 안 잡힌다.

## ★6단계 — 사진을 실제로 내려받아 눈으로 보고 첨부한다 (필수)

URL만 넘기면 운영자가 하나씩 열어봐야 한다. **파일을 받아 직접 보고, 원본을 채팅에 첨부**한다.
프록시가 직접 다운로드를 막으므로(`CONNECT tunnel failed, 403`) **Make를 통해 base64 조각으로 가져온다.**

### 흐름
```
1 ParseJSON  [{k:"f1", u:"<사진 URL>"}, ...]          ← 카드에 쓸 사진만, 5~6장
2 Iterator   URL마다
3 HTTP       GET 이미지 (parseResponse=false)
             ★헤더 Referer: https://korean.visitkorea.or.kr/  ← 없으면 막힐 수 있다
4 Iterator   {{split("0,1,2,...,21"; ",")}}            ← 조각 번호
5 AddRecord  key=IMG_<k>_<i>
             {{substring(toString(base64(3.data)); 조각*14000; (조각+1)*14000)}}
```
HTTP는 URL당 1회만 돌고(모듈 3), 조각 나누기만 22번 반복된다. 5장이면 5 HTTP + 110 저장.

### 로컬에서 재조립
```python
# 데이터스토어에서 IMG_* 레코드를 받아 조각 번호 순으로 이어붙인 뒤
open(f"{name}.jpg","wb").write(base64.b64decode(b64))
```

### ★반드시 지킬 4가지 (전부 실제로 겪음)
**1. 잘림을 반드시 검사한다.** 조각이 모자라면 아래쪽이 회색으로 날아간다.
```python
im = Image.open(p); im.load()   # 잘렸으면 여기서 예외
```
　★실제: 승일교 사진을 14조각(=147,000B 상한)으로 받았더니 하단 20%가 잘렸다. 22조각으로 다시 받아 194,038B로 완성.
　마지막 조각 길이가 14000이면 **아직 안 끝난 것**이다. 0이 나올 때까지 조각 수를 늘린다.

**2. 데이터스토어는 1MB다.** 사진 두세 장이면 찬다.
　`Maximum data store size (1024 KiB) will be exceeded` → **재조립이 끝난 `IMG_*` 레코드는 즉시 삭제**하고 다음 장을 받는다.

**3. `_image2_1`(웹용)과 `_image3_1`(썸네일)이 있다.** 썸네일은 17KB라 한 조각에 들어가지만 카드로 쓰기엔 작다. **카드용은 `_image2_1`**.

**4. 받은 사진을 Read로 열어 눈으로 본다.** 이게 이 단계의 진짜 목적이다.

### ★눈으로 봐야만 잡히는 것 — 2026-09 철원에서 셋 다 나왔다
| 무엇 | 실제 사례 |
|---|---|
| **파일명이 내용과 다르다** | `강원_철원_고석정국민관광지_전경`이 실제로는 **인공 폭포**였다. 정자도 꽃밭도 아니다 |
| **사진 안에 글자·간판이 있다** | 고석정 꽃밭 컷 하나에 **"I LOVE CHEORWON" 조형물**이 크게 박혀 있었다 → "사진 안 글자 0" 규칙 위반이라 배경에서 탈락 |
| **이미 워터마크가 있다** | 관광공사 사진은 **우하단에 한국관광공사 워터마크**가 박혀 있다 → 우리 워터마크는 **좌하단**으로 옮긴다 |

★**사진과 카드 문구가 서로 맞는지도 본다.** 나무 그늘 가득한 폭포 사진에 "그늘이 적어요"를 얹으면 독자가 헷갈린다(실제로 그렇게 만들었다가 고쳤다).

### 첨부
`SendUserFile`로 **글자 없는 원본**을 그대로 보낸다. 파일명은 `photo01.jpg`처럼 ASCII로(한글 파일명은 첨부에서 깨진다).
카드별로 어느 사진을 쓰면 되는지, 그리고 위에서 발견한 주의점을 한 줄씩 붙인다.

### 오퍼레이션 예산
검색어 1개당 약 3회. 10개 ≈ 30회. 키워드 실측(155개 ≈ 470회)에 비하면 무시할 수준이다.

## ★사진을 눈으로 확인하는 법

**Claude는 사진을 볼 수 없다.** 프록시가 외부 접속을 막아 URL을 열 수 없고,
API가 주는 건 제목·유형·URL 같은 **텍스트뿐**이다. "이 사진이 카드에 어울리는가"는 판단할 수 없다.

→ 그래서 **후보를 한 장에 모은 HTML을 만들어 운영자에게 보낸다.**
　`<img src="...">`를 격자로 깔고 사진마다 `Type1/Type3`를 색으로 표시하면
　운영자가 스크롤 한 번으로 고를 수 있다. (2026-09-07 철원 78장에 이 방식을 썼다)

→ 그래서 **영문 프롬프트에 장면 묘사를 쓰지 않는다.**
　`a wide-open flower field with pink muhly in soft focus…`처럼 상상한 장면을 적으면
　실제 사진이 다를 때 **모델이 배경을 그 묘사대로 고쳐 그린다.**
　대신 이렇게만 쓴다:
```
Edit the uploaded photograph. Keep the image EXACTLY as-is — do NOT repaint,
redesign, regenerate, restyle or replace any part of the background.
ONLY overlay Korean text and a watermark.
Place the text on whichever area of the photo is naturally brightest and
least busy; if no such area exists, place it across the lower third.
```

## ★2026-09-10 정읍에서 해결 — **사진 다운로드가 처음으로 성공했다** (3연패 종료)

세 번 연속 실패했던 6단계(사진 원본 내려받기)가 이번에 돌았다. 원인은 둘 다 이 문서의 예시 자체에 있었다.

### 원인 1 — `(조각+1)`이 Make에서 **문자열 연결**로 처리된다
이 문서가 적어 둔 `{{substring(toString(base64(3.data)); 조각*14000; (조각+1)*14000)}}`에서
`4.value`는 `split()`이 준 **문자열**이라 `4.value + 1`이 덧셈이 아니라 **연결**이 된다.
`"26" + 1` → `"261"` → 끝 인덱스 `3,654,000`. 그래서 조각 하나가 14,000자가 아니라 **14만 자**로 부풀어
레코드 7개만에 943KB를 먹고 `OutOfSpaceError`가 났다. 세 번의 실패가 전부 이것이다.

**고친 표현식 — 이걸 쓴다**
```
{{substring(toString(base64(3.data)); 4.value * 14000; 4.value * 14000 + 14000)}}
```
`4.value * 14000`이 먼저 숫자로 강제되므로 뒤의 `+ 14000`은 정상적인 덧셈이 된다.

### 원인 2 — 재조립하려고 레코드를 읽으면 **내 컨텍스트가 터진다**
사진 한 장이 base64로 20만 자다. `data-store-records_list` 결과를 그대로 받으면 5만 토큰이 날아간다.
→ **결과가 크면 도구가 알아서 파일로 떨궈 준다.** 그 경로를 python으로 읽어 재조립하면 컨텍스트를 1도 안 쓴다.
```python
recs = json.loads(io.open(저장된_경로, encoding='utf-8').read())
# IMG_<k>_<i> 를 i 순서로 이어붙여 base64.b64decode → .jpg
```

### 시나리오
`🖼 사진 원본 내려받기 (base64 조각)` — id **6219674** (on-demand · 이번에 새로 만들었다)
데이터스토어는 `146191` 공용. **한 번에 2장까지**(30조각 기준 약 400KB). 큰 사진은 33~45조각.

### 조각 수 판정 (문서의 기존 규칙이 맞았다)
- **마지막 조각 길이 0자 = 다 받은 것.** 14,000자면 **아직 안 끝났다** → 조각 수를 늘려 다시.
- 실측: 15만~22만 바이트 사진은 30조각으로 충분. 30만 바이트대는 30조각으로 **잘렸다**(45조각 필요).
- PIL이 이 환경에 없다. 대신 **JPEG 마커로 검사**한다 — `d[:2]==b'\xff\xd8' and d[-2:]==b'\xff\xd9'`.

### ★그리고 눈으로 봐서 실제로 한 장을 걸러냈다
`전북_정읍_우화정_외부_05.jpg`(Type1)를 열어 보니 우화정이 아니라 **캐릭터 포토존 프레임**이었고
사진 안에 글자가 세 곳 박혀 있었다. URL과 유형만 보고 넘겼으면 그대로 배경으로 썼을 컷이다.
**이 단계의 값어치가 여기서 나온다.**

## ★2026-09-11 안동에서 겪은 것 — **`contentTypeId=12`를 안 붙이면 여행코스가 잡힌다**

하회마을 사진을 받으려는데 **이미지가 0장**으로 나왔다. 장소가 없어서가 아니었다.

| 검색어 | 잡힌 것 | 이미지 |
|---|---|---|
| `안동하회마을` | `세계문화유산에 빛나는 안동하회마을` (**contenttypeid 25 = 여행코스**) | **0장** |
| `하회마을` | `너무도 유명한 안동 하회마을 여행 코스` (**25**) | **0장** |
| **`안동 하회마을` + `contentTypeId=12`** | **`안동 하회마을 [유네스코 세계유산]` contentid 894027 · Type1** | **다수** |

`searchKeyword2`는 관광지(12)·축제(15)·여행코스(25)를 한 통에 넣고 돌려준다.
**여행코스(25)에는 `detailImage2`로 받을 이미지가 없다.** 그래서 시나리오가 `item[1]`을 집으면 빈손이 된다.

★**해법 — 모듈 3의 `qs`에 `contentTypeId=12`를 추가한다.** (검색은 소문자 `contentTypeId`, detailImage2는 `contentId` — 둘 다 대문자 I·T다)
```
{"name": "contentTypeId", "value": "12"}
```
이걸 붙인 뒤 `안동 하회마을`·`병산서원`·`부용대`·`월영교`가 전부 한 번에 잡혔다.

★**함께 확인된 것** — 검색어에 **공백을 넣는 편이 낫다.** `안동하회마을`(붙여쓰기)은 여행코스 제목과 더 잘 붙는다.

### 안동에서 나온 저작권 분포 (사진 단위로 갈린다는 증거가 또 나왔다)

## ★2026-09-11 고창에서 겪은 것 두 가지 — **둘 다 도구를 못 쓰게 만드는 함정이었다**

### 1. `arrange=A`(제목 가나다순)가 엉뚱한 걸 `item[1]`에 올린다

`선운사`로 검색하면 `totalCount`가 **2건**인데, 가나다순이라 이렇게 온다.

| 순서 | title | contentid | cpyrhtDivCd | 실제 |
|---|---|---|---|---|
| `item[1]` | **선운사 백파율사비** | 1596506 | **Type3** | ⚠**비석**이다. 절이 아니다 |
| `item[2]` | **선운사(고창)** | **147548** | **Type1** | ★**절 본체.** 사진 12장 중 Type1이 5장 |

그래서 1차 시도에서 **비석 사진을 절 사진으로 착각**하고 "절 본체 컷은 못 구했다"로 넘겼다.
CREDITS에 `⛔미확보 — 선운사 대웅보전·일주문 전경`이라고 적기까지 했는데, **사진은 처음부터 있었다.**

★**해법 — 검색과 이미지를 두 단계로 쪼갠다**
```
[1단계] searchKeyword2만 돌려 응답 전체를 데이터스토어에 저장 (key = ZS_<검색어>)
        numOfRows를 10으로, 저장 substring을 3000자로 올린다
        → title·contentid·cpyrhtDivCd를 눈으로 보고 contentid를 고른다
[2단계] 고른 contentid를 모듈 1의 json에 c로 박아 detailImage2만 돌린다 (key = ZI_<이름>)
```
`item[1]`을 믿지 않는다. **제목을 눈으로 보고 고른다.** 1건이 아니라 2건 이상이면 반드시 이 단계를 거친다.

### 2. `data-store-records_list`의 `pg[offset]`이 먹지 않는다

`pg[offset]`을 9로 주든 6으로 주든 **매번 같은 앞 10건**이 돌아온다.

45조각짜리 사진은 한 번에 다 못 읽는다.

★**해법 — 읽은 레코드를 즉시 지우고 다시 list 한다.** 이게 유일한 페이징 수단이다.
```

```
이 문서가 원래 "1MB 제한 때문에" 즉시 삭제를 시켰는데, **사실은 페이징 때문에도 필수**였다.
마지막 조각 길이가 **0이면 그 사진은 끝**이다 — 거기서 이어붙여 `b64decode` 하면 된다.

### 3. 이번에도 눈으로 봐서 한 장을 걸렀다 (세 번째)
`3587082`(Type1)는 **연등 사진인데 등마다 한글이 빽빽이 인쇄**돼 있었다 — "사진 안 글자 0" 위반.
게다가 **부처님오신날(4~5월)** 장면이라 9월 글과 계절도 안 맞는다.
(철원 `I LOVE CHEORWON` 조형물 · 정읍 캐릭터 포토존에 이어 세 번째다.)

### 4. ★사진과 카드 문구가 서로 맞는지를 배정 기준으로 삼는다
같은 절 사진인데 **`3587088`은 평탄한 흙길**, **`3587074`는 계단이 보인다.**
본문이 "계단을 올라야 나오는 절이 아니에요"라고 말하는 무장애 카드에 후자를 쓰면 **사진이 본문을 반박한다.**
→ 장소가 같다고 아무 컷이나 돌려 쓰지 않는다. **그 카드가 주장하는 것을 사진이 증명하는지** 본다.

### 5. 다른 지역 사진을 빌려 오지 않는다
`꽃무릇` → **함평 용천사**(Type3) / `상사화` → **영광 불갑**. **고창 꽃무릇은 API에 없다.**

　카드 문구로 "여기가 그 자리다"를 말하게 했다. 지역이 틀린 사진은 한 번 들키면 글 전체의 신뢰가 깨진다.

## 2026-09-12 · 속초 사진 내려받기에서 컨텍스트 11만 토큰을 태웠다 — 원인과 해법

★**증상**: `data-store-records_list` 한 번에 base64 덩어리가 **파일로 저장되지 않고 응답 본문에 통째로** 실려 왔다.
두 번 반복돼 약 11만 토큰이 컨텍스트로 들어갔고, 그 회차의 사진 확보를 포기해야 했다.

### 1. 파라미터 이름이 바뀌었다 — `pg[limit]` → `limit`
MCP 재연결 뒤 `data-store-records_list`가 **`limit`** 을 받는다. `pg[limit]`는 더 이상 통하지 않는다.
★MCP 접두어뿐 아니라 **파라미터 이름도 세션마다 바뀔 수 있다.** 첫 호출은 반드시 **작은 값(limit=1)**으로 찔러 보고,
　응답이 파일로 갔는지 본문으로 왔는지 **눈으로 확인한 뒤** 본 호출을 한다.

### 2. ★응답이 짧으면 파일이 아니라 '본문'으로 온다 (이게 진짜 원인)
MCP 응답은 **약 140,900자를 넘을 때만** 툴 결과 파일로 빠진다. 그 아래면 **본문에 인라인으로 박힌다.**
내려받기 시나리오 6219674는 조각 슬롯을 **45개** 잡아 두는데, 실제 사진이 20조각이면 **나머지 25개가 빈 레코드**다.
빈 레코드가 섞이면 응답 총길이가 상한 아래로 내려가고 → **base64가 그대로 컨텍스트에 쏟아진다.**
즉 "조각이 적어서 안전"이 아니라 **조각이 적을수록 위험**하다. 직관과 반대다.

★**해법 — 조각 공급을 그 사진에 필요한 개수로 정확히 맞춘다.**
```
190KB 사진 → 조각 20개면 충분 → 시나리오의 split 를 "0,1,2,…,19" 로 넣는다 (45 고정 금지)
→ 모든 list 호출이 '꽉 찬 조각 10개'로 돌아오고, 길이가 상한을 넘어 항상 파일로 저장된다
```
꼬리의 빈 레코드를 남기지 않는 것이 핵심이다. 파일 크기를 모르면 먼저 `detailImage2`의 URL로
**HEAD/Content-Length만 확인**하거나, 20조각으로 돌려 보고 마지막 조각 길이가 0이 아니면 늘린다.

### 3. 손실을 막는 절차 (다음 회차에 그대로 따를 것)
1. `limit=1`로 한 건만 읽어 **응답이 파일로 갔는지** 확인한다. 본문으로 오면 즉시 중단.
2. 본문으로 왔다면 → 조각 수를 맞춰 시나리오를 다시 돌리고, **그 전에 데이터스토어를 싹 비운다.**
3. 읽은 레코드는 즉시 `data-store-records_delete` (페이징 수단이자 안전장치).
4. 한 장에 두 번 실패하면 **그 회차는 포기하고 CREDITS에 '미확보·운영자 몫'으로 기록한다.**
　 사진 한 장 때문에 그 회차의 집필·평가를 통째로 날리는 게 더 큰 손해다.

## ★2026-09-29 (20회차 구례) — base64 우회의 두 가지 결정적 개선

### 개선 1 — 손으로 옮겨 적지 마라. 툴 결과가 **파일로 저장**된다

16회차 횡성에서 base64 재조립이 깨진 원인은 **내가 조각을 컨텍스트에서 파일로 옮겨 적다가 2글자를 틀린 것**이었다.
그런데 `data-store-records_list`의 결과가 크면 하네스가 이렇게 답한다:

```
Error: result (487,066 characters across 268 lines) exceeds maximum allowed tokens.
Output has been saved to /root/.claude/projects/<proj>/<session>/tool-results/mcp-Make-data-store-records_list-<ts>.txt
```

★**이 파일을 파이썬으로 직접 읽으면 base64가 내 컨텍스트를 한 글자도 거치지 않는다.**
옮겨 적는 단계가 사라지므로 **전사 오류가 원천적으로 불가능**하다. 컨텍스트 비용도 0이다.

```python
import json, base64, io
recs = json.load(io.open(SAVED_FILE, encoding="utf-8"))
d = {r["key"]: r["data"]["measuredAt"] for r in recs}
b = "".join(d.get("IMG_%s_%02d" % (k, i), "") or "" for i in range(18))
assert len(b) == d["IMG_%s_LEN" % k] and len(b) % 4 == 0
open(fn, "wb").write(base64.b64decode(b))
```

→ **결과가 파일로 안 떨어질 만큼 작으면 오히려 손해다.** 일부러 크게 만들어도 된다(조각을 크게).

### 개선 2 — `LEN` 레코드를 반드시 같이 저장한다

조각을 뜨기 전에 총 길이를 따로 저장해 두면 **재조립이 맞았는지 즉시 판정**된다.

```
module id 6 (id 4 조각 피더보다 먼저):
  key  : IMG_{{2.k}}_LEN
  value: {{length(toString(base64(3.data)))}}
```

검증 3종 — `len(joined) == LEN` · `len % 4 == 0` · JPEG 매직(`\xff\xd8\xff`)과 EOI(`\xff\xd9`).
세 개가 다 통과해야 파일로 쓴다. 하나라도 어긋나면 쓰지 말고 다시 받는다.

### 개선 3 — 조각 크기를 2,600 → 18,000으로 키워 **원본 해상도**를 받는다

옛 설정(18조각 × 2,600 = 46,800자)으로는 **썸네일(`_image3_1.jpg`, 300×200)밖에** 못 받았다.
카드 배경으로 쓰기엔 너무 작다. 조각을 18,000자로 키우면 **18 × 18,000 = 324,000자**까지 담기고,
이는 관광사진 원본(`_image2_1.jpg`, **940×626**)을 충분히 덮는다.

실측 원본 base64 길이 (참고):
```
화엄사 127923       255,572자 → 191,678B → 940×626
화엄사계곡 126266   314,964자 → 236,223B → 940×626
연곡사 126363       259,752자 → 194,813B → 940×626
피아골계곡 126265   228,028자 → 171,019B → 940×626
```
→ **먼저 LEN만 뽑는 런을 한 번 돌려 크기를 재고**, 그다음 조각 런을 돌리면 헛돈을 안 쓴다.
→ 한 번에 2장씩 돌리는 게 안전했다(4장을 한 런에 넣으면 응답이 커진다).

### ★사진을 받은 뒤 반드시 '열어서' 볼 것 — 20회차에 실제로 걸러낸 것들

파일이 멀쩡히 열려도 **글에 쓸 수 있느냐는 다른 문제**다. 구례 4장에서 실제로 나온 문제:

| 사진 | 문제 |
|---|---|
| 화엄사 127923 | **매화가 핀 봄 장면.** 단풍 글의 히어로로 계절이 안 맞는다 |
| 피아골계곡 126265 | **짙은 초록 여름.** 단풍 글인데 단풍이 없다 |
| 화엄사계곡 126266 | 초록 여름. 무난하지만 평범 |
| 연곡사 126363 | ★**현판에 한자가 박혀 있다.** image-guide의 "사진 안엔 글자·간판 0" 위반 → **오버레이 배경으로 못 쓴다**(본문 삽입용으로는 가능) |

★**결론: `cpyrhtDivCd`가 Type1이어도 그 사진을 오버레이 배경으로 쓸 수 있다는 뜻이 아니다.**
　라이선스(Type1/Type3)와 **사용 적합성(계절·글자·구도)** 은 별개 관문이다. 둘 다 통과해야 한다.
★관광사진 API는 **계절을 고를 수 없다.** 단풍·벚꽃 같은 계절 글은 API만으로 히어로를 못 채울 수 있으니,
　확보한 사진의 계절을 먼저 확인하고 안 맞으면 **운영자에게 교체를 요청**한다(가짜 생성 배경으로 때우지 않는다).
